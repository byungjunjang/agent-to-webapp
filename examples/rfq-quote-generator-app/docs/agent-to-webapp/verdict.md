### 세 실행 공통으로 다른 점

1. **입력을 읽은 시점과 경로.** 세 보고 모두 Read 를 Step 0 다음 "Step 1 스펙 추출" 에 적었다. 기록을 보면 세 실행 모두 사전 확인 중 Step 0(`init_customer.py`) 보다 먼저 입력 두 파일을 읽었다(run-1 #3·#4, run-2 #4·#5, run-3 #2·#3). 읽은 곳도 `input/<고객사>/` 사본이 아니라 `runs/inputs/<폴더>/` 원본이다. Step 0 의 복사본은 Step 1 입력으로 한 번도 쓰이지 않았는데, `extracted_specs.json` 의 `source_files` 에는 세 번 모두 `input/<고객사>/…` 로 적혀 있다. 원인은 CLAUDE.md 순서 자체에 있다. Step 0 폴더 이름(고객사 약칭)은 `customer_company` 에서 뽑는데 그 값은 Step 1 에서야 나온다
2. **`evaluate_routes.py` 가 Step 2 보다 먼저 돌았다.** 세 실행 모두 Step 1 검증과 1–2초 간격으로 붙어 있다(run-1 #9→#10, run-2 #28→#29, run-3 #25→#26). run-2·run-3 은 이를 "Step 1 검증과 병렬" 로 보고했다. run-1 은 Step 2 다음 Step 3 안에 적었다
3. **"스킬" 사용.** 보고서는 단계마다 "스킬 rfq-spec-extractor" 같은 식으로 스킬을 도구로 적었다. 그런데 Skill 도구 호출은 세 실행을 통틀어 run-2 #3(`rfq-spec-extractor`) 한 번뿐이다. 나머지는 SKILL.md 를 `cat`(run-1 #2) 이나 Read(run-2 #10·#13·#16, run-3 #6·#9·#12·#15) 로 읽었다. 스킬은 호출되지 않고 지침 문서로 읽혔다
4. **Step 4 검증.** 세 보고 모두 "모든 값 양수, quote > unit_cost > 0 충족" 이라고 적었다. run-1·run-2 에는 이를 확인한 도구 호출이 없고, 모델이 `cat` 출력(run-1 #13, run-2 #33)을 보고 판단했다. 코드로 확인한 것은 run-3 마지막의 python assert(#41) 하나다

일치를 확인한 것: 세 보고의 "공용 스킬 스크립트는 고치지 않음" 은 기록과 맞다. Write/Edit 대상은 `output/<고객사>/` 파일과 run-N.md 뿐이다. 도면 복사 실패, `cp`+`cmp` 대체, 참고값 산출 코드, xlsx 셀 보정 내용, grep 검증도 기록과 맞다.

## 2. 모든 실행에서 순서와 방식이 같았던 단계

실제 순서는 세 실행이 같다.

사전 확인 → 입력 2개 Read(원본 폴더) → Step 0 `init_customer.py` → Step 1 JSON Write → `validate_specs.py` 와 `evaluate_routes.py` → Step 2 Edit(`missing_specs`) → Step 3 route_evaluation.json Write → Step 4 `calculate_quote.py` → Step 5 route_evaluation.json 재작성 → Step 7 이메일 ko → zh → en → Step 6 `generate_quote_xlsx.py` → 최종 검증 → run-N.md

CLAUDE.md 와 다른 곳은 세 군데다. 입력 읽기가 Step 0 보다 먼저이고, Step 3 스크립트가 Step 2 보다 먼저이고, Step 7 이 Step 6 보다 먼저다. 세 실행 모두 똑같이 이렇게 했다. 문서 순서와 다를 뿐 실제 순서는 고정돼 있다. Step 3 스크립트는 `missing_specs` 를 쓰지 않고, 이메일은 xlsx 파일을 입력으로 쓰지 않으니 이 순서가 의존 관계에도 맞다.

순서와 방식이 모두 같았던 단계:

1. **입력 읽기** — 입력 두 파일을 Read 로 직접 읽었다. PDF 든 md 든 같은 방식이다. 입력 PDF 는 Pillow 로 만든 이미지 PDF(DCTDecode)라서 텍스트 규칙이 아니라 모델이 읽었다
2. **Step 1 스키마 검증** — Write 뒤 재작성 없이 `validate_specs.py` 가 세 번 모두 PASSED 였다. 재추출은 0회
3. **Step 3 범위 매칭** — `evaluate_routes.py` 를 CLAUDE.md 명령 그대로 Step 1 검증 직후에 돌렸다. 출력도 세 번 같다(VCQ·GC 는 범위 안, GN 은 범위 밖, 재질 유효)
4. **Step 3 루트 status** — 세 번 모두 진공 `recommended`, 가스침탄 `candidate_not_recommended`, 질화 `not_suitable` 이고 인용한 규칙 조항도 같다(§2-A 추천 3조건, §2-B candidate 조건, §2-C ECD 상한 > 0.40). 다만 세 입력의 도면이 같은 파일이라, 이 일치는 입력이 같아서 나온 것이다(7절)
5. **Step 4 본 계산** — CLAUDE.md 명령 그대로 stdout 을 리디렉션했다. 결과 차이는 lot_size 입력 차이에서만 나온다(1,200 / 2,500 / 1,000)
6. **Step 6 견적서 생성 호출** — `generate_quote_xlsx.py` 를 CLAUDE.md 명령 그대로 호출했고 파일명 규칙(`견적서_[rfq_number].xlsx`)도 같다
7. **Step 7 파일 구성** — 한/중/영 3개 파일을 같은 이름으로 ko → zh → en 순서로 썼다. 내용 구성은 3절

## 3. 실행마다 달랐던 단계

1. **사전 확인** — 단계 추가, 방법 다름
   - 무엇이: run-1 은 `cat` 으로 규칙·스킬·스크립트·채점표를 읽었다. run-2 는 Skill 도구 1회와 Read 를 쓰고 run-1.md 와 NovaDrive 산출물 5개를 추가로 읽었다. run-3 은 Read 를 쓰고 run-1.md·run-2.md, Helios 산출물 3개, 채점표, 훅 설정을 추가로 읽었다
   - 왜: 앞 실행의 기록과 산출물이 같은 폴더에 있었고 에이전트가 이를 선례로 삼았다. 그 결과 run-2 는 run-1 의 질화 리드타임 `risk` 를 `null` 로 뒤집었다. run-3 는 run-2 의 가정 문구와 `null` 처리를 그대로 가져왔고, 복사 실패 대체 경로를 미리 넣었다
2. **Step 0 입력 파일 준비** — 방법 다름
   - 무엇이: run-1 은 도면 복사에 실패해 md5 가 같은 기존 `input/NovaDrive/` 파일을 썼다. run-2 도 도면 복사에 실패해 `cp`+`cmp` 로 대신했다. run-3 는 대체 경로를 미리 넣었지만 두 파일 모두 스크립트로 복사됐다. 고객사 약칭은 NovaDrive·Helios 는 `customer_company` 에서 뽑았고, Orion 은 회사명이 없어 입력 폴더 이름과 메일 도메인에서 정했다
   - 왜: 경로 길이 260자 제한 때문이다(1절 run-3). 환경에서 오는 결정론적 원인이다
3. **Step 1 스펙 추출** — 방법 다름
   - 무엇이: 필수 17필드는 같다. 보조 필드는 실행마다 새로 만들었다. run-1 은 `drawing_rev`·`delivery_basis`·`rfq_subject` 등, run-2 는 `customer_part_no`·`lot_basis`·`straightening_allowed`·`packing_requirement`·`ppap_requirement`·`customer_requested_reply_items` 를 더했고, run-3 은 `material_confirmed`·`*_source`·`assumed_fields` 를 더했다
   - 값 해석: run-2 는 lot_size 를 첫 로트 2,500 으로 잡았다(월 5,000·연 60,000 도 후보였다). "6 weeks" 는 42 로 바꿨다. run-3 은 이메일의 "steel" 대신 도면의 SCM420H 를 잠정값으로 썼다. 입력에 없는 lot_size 1,000, delivery_days 12, customer_name "구매 담당자", customer_company(도메인 추정), rfq_number `INT-ORION-260911` 은 지어 넣고 `*_source: assumed` 로 표시했다
   - 왜: 입력마다 정보 구조가 다르다. 스키마가 17필드만 정해 두어 나머지 필드는 모델이 필요할 때마다 만들었다. run-3 에서는 `validate_specs.py` 가 lot_size·delivery_days 양수를 요구하는데 CLAUDE.md 에러 처리 표에 "고객이 정보를 주지 않음" 이 없다. 그래서 멈추는 대신 가정값을 넣어 검증을 통과시켰다
4. **Step 2 누락 스펙** — 방법 다름, 재검증 위치는 순서가 바뀜
   - 무엇이: run-1 은 §3 의 6개를 전부 넣었다. run-2 는 3개를 넣고, RFQ 가 정한 3개는 규칙에 없는 `checklist_defined` 배열에 따로 적었다. run-3 은 9개를 넣었다. `category: quote_basis` 3개(재질·수량·납기)와 `checklist` 6개다. 마스킹·샘플링·측정 위치의 가정 문구는 run-1 것이 run-2·run-3 에 거의 그대로 쓰였다. 재검증은 run-1 이 Step 4 뒤, run-2·run-3 은 Step 3 JSON 뒤에 했다
   - 왜: 입력마다 정의된 항목 수가 다르다. 이 차이는 정상이다. 스키마 확장은 규칙에 없어서 즉석에서 만들었다. CLAUDE.md 는 "6개 항목 확인" 이고 §3 은 "Typical missing items" 라 목록이 열려 있다. 두 문서가 어긋나고, run-3 은 §3 쪽을 따라 목록 밖 항목을 넣었다
5. **Step 3 판정 JSON** — 방법 약간 다름
   - 무엇이: status 는 같다. run-3 만 `conditional_on`(재질 확정 조건) 필드를 더했다. run-2 는 고객이 교정을 허용했는데도 규칙 문구대로 `candidate_not_recommended` 를 유지했다
   - 왜: run-3 의 재질이 잠정값이다. 규칙에 교정 허용으로 판정을 바꾸는 조항이 없다
6. **Step 4 참고 수치 추가 산출** — 단계 추가
   - 무엇이: run-1 은 `calculate()` 를 import 해 status 만 바꾸고 질화 참고값(19.9 hr / 5 batch / 23.41)을 냈다. run-2 는 질화 참고값에 월 5,000 로트 참고 단가(12.84 / 7.34)를 더했다. run-3 은 질화 참고값에 수량별 단가표 5행(219 / 500 / 1,000 / 2,000 / 5,000 pcs)을 더했다. 저장한 필드 이름도 `reference_economics`·`serial_lot_reference`·`lot_sensitivity` 로 매번 달랐다
   - 왜: run-1 은 채점표가 질화 수치를 기대해서, run-2 는 수량이 "첫 로트 + 월 물량" 구조라서, run-3 은 수량이 없어서다. 규칙 §6("For each candidate route … cycle time, batch count, rough quote")에 not_suitable 루트가 포함되는지도 불분명하다
7. **Step 5 리드타임** — 방법 다름
   - 무엇이: 질화(not_suitable)의 `lead_time_assessment` 가 run-1 은 `risk`, run-2·run-3 은 `null` 이다. run-3 은 delivery_days 가 12일(가정값)인데도 §5 의 "≤12일 요청이면 risk" 를 적용하지 않았다
   - 왜: 스킬은 "각 valid 루트에" 부여하라고 하고 규칙 §5 는 질화에 risk 를 준다. 두 문서가 어긋난다. run-2 가 run-1.md 를 읽고 `null` 로 바꿨고 run-3 이 따랐다. 세 실행 모두 요청 납기가 12일 이상이라(12, 42, 가정 12) feasible·risk·not_feasible 의 경계는 한 번도 시험되지 않았다. 규칙에도 경계가 수치로 없다("10-12 days feasible")
8. **Step 7 회신 이메일** — 방법 다름
   - 무엇이: run-1 은 템플릿 순서(요약 → 대안 → 확인 요청 → 납기 → 첨부)를 따랐다. run-2 는 리드타임을 확인 요청 앞으로 옮기고 "검사 항목" 절을 더했고, 단가에 반영되지 않은 비용(교정·PPAP·트레이)을 적었다. run-3 은 "잠정 견적(가정 기준)" 으로 시작해 수량별 단가표를 넣고, 확인 요청을 A(견적 전제, 회신 필수)와 B(공정·품질, 가정 포함)로 나누고, RFQ 번호와 담당자명을 요청했다. 호칭도 "Mr./Ms. Li", "Dear Maria Keller", "Dear Sir or Madam" 으로 달랐다. run-3 만 작성 직후 Edit 를 2회 했다
   - 왜: 고객이 요구한 회신 항목이 다르다(run-2 는 "inspection items" 를 명시했다). run-3 은 견적 안내보다 정보 요청이 회신의 목적이 됐다
9. **Step 6 견적서 사후 보정** — 단계 추가·생략
   - 무엇이: run-1 은 보정하지 않았다. 리드타임 칸 "feasible" 과 비고 "납기: 첫 배치 PO 수령 후 조건 확인 필요" 가 RFQ 의 12일과 맞지 않는데도 그대로 뒀다. run-2 는 openpyxl 로 비고 2줄을 바꾸고 3줄을 더했다. run-3 은 셀 주소(A11, F4, C19, C25, C29, A46)를 하드코딩해 6칸을 바꾸고 3줄을 더했다
   - 왜: `generate_quote_xlsx.py` 는 비고의 납기·포장 문구를 고정 문자열로 쓰고, 리드타임 칸에 enum 을 그대로 넣고, `packing_requirement`·`delivery_days`·`*_source`·참고 단가를 읽지 않는다. 입력이 스크립트의 전제에서 멀어질수록 보정이 늘었다. 보정할지 말지 정하는 기준은 어디에도 없다
10. **최종 검증** — 방법 약간 다름
    - 무엇이: 기본 방식은 같다(openpyxl 셀 덤프 + 이메일 grep). run-3 만 route/quote 조건을 python assert 로 확인했다. grep 할 문자열은 매번 모델이 그 실행의 값에서 골랐다
    - 왜: 검증 항목이 스킬에 문장으로만 있고 검사 코드가 없다

## 5. 4번째 칸 항목과 규칙화 의견

순서 자체가 흔들린 항목은 없다. 세 항목 모두 단계가 상황 따라 추가됐거나 방식이 즉흥이었던 경우다. 원인은 규칙과 스크립트의 빈틈(에러 처리 표 누락, 템플릿 고정 문구, §6 모호)이다. 빈틈을 메우면 결정론 쪽으로 옮길 수 있다.

1. **견적 전제 누락 시 진행 방식** — 분기 조건과 산출물 형식은 규칙으로 바꿀 수 있다. 가정값을 고르는 일은 규칙이 아니라 사람에게 맡겨야 한다
   - Step 1 이 필드마다 출처(`rfq` / `drawing` / `assumed` / `missing`)를 내게 한다. `lot_size`·`delivery_days`·`material` 중 하나라도 출처가 rfq 나 drawing 이 아니면 "잠정 견적 모드" 로 간다. 이 판별은 코드로 할 수 있다
   - 잠정 모드에서 할 일을 고정한다. (a) 사람 확인 단계에서 영업 담당이 수량·납기를 넣거나 가정값을 승인한다. (b) JSON·견적서·이메일 세 곳에 가정 표시를 한다. (c) 이메일 확인 요청은 "견적 전제" 와 "공정·품질 조건" 두 묶음으로 나눈다. (d) 수량별 단가표를 붙인다
   - 지금 `validate_specs.py` 는 양수만 받아서 모델이 값을 지어내게 만든다. 고정 워크플로우에서는 `null` 과 출처를 받고 분기에서 처리해야 한다. CLAUDE.md 에러 처리 표에도 이 경우를 넣어야 한다
   - 남는 불확실성: 무엇을 누락으로 볼지(예: "steel" 을 재질 누락으로 볼지)는 Step 1 의 LLM 이 정하므로 분기의 입력은 여전히 확률적이다. 이 분기는 관찰에서 한 번만 나타났다
2. **Step 6 견적서 사후 보정** — 규칙으로 바꿀 수 있다. 템플릿을 고치면 이 단계가 없어진다
   - 보정한 내용은 모두 JSON 에 이미 있는 값이다. 비고의 납기(`delivery_days`·`delivery_basis`), 포장(`packing_requirement`), 고객 지정 조건(교정·PPAP), 리드타임 칸(`lead_time_days`), 가정 표시(`*_source`), 참고 단가다. 견적서 생성 함수가 이 필드를 읽으면 보정은 결정론 단계인 Step 6 안으로 들어간다
   - 지금 방식(생성 뒤 셀 주소를 하드코딩해 덮어쓰기)은 `missing_specs` 개수가 바뀌면 행이 밀려서 깨진다. 웹 앱으로 가져가면 안 된다
3. **Step 4 참고 수치 추가 산출** — 규칙으로 바꿀 수 있다. 계산할 목록을 고정하면 된다
   - 제안하는 목록은 셋이다. (a) not_suitable 루트도 참고값을 항상 계산하되 견적서 품목에는 넣지 않는다. 규칙 §6 해석을 이렇게 명시한다. (b) `monthly_volume` 이 lot_size 와 다르면 그 수량으로도 단가를 낸다. (c) 잠정 모드면 정해진 수량 목록(1배치 만재, 500, 1,000, 2,000, 5,000)으로 단가표를 낸다. 저장 필드 이름은 하나로 통일한다
   - 계산 자체는 이미 `calculate()` 를 재사용해서 결정론이다. 흔들린 것은 "무엇을 계산할지" 뿐이다. 특이한 수량 구조처럼 영업 판단이 필요한 경우는 1번의 사람 확인 단계에서 추가 수량을 받는다

## 6. 고정하면 품질이 떨어질 단계

- **가정 수량 기본값**: 수량에 따라 진공침탄 단가가 12.76(219 pcs)에서 16.63(500 pcs)까지 30% 가까이 움직인다. 기본값(예: 1,000)을 규칙으로 박으면 소량 고객에게 과소 견적이 나간다. 사람이 넣게 해야 한다
- **누락 스펙 가정 문구**: run-2·run-3 은 run-1 문구를 거의 그대로 썼고 같은 도면이라 맞았다. "나사부 E(M16x1.5) 방탄", "D 구간 단면 HV" 는 이 도면에만 해당한다. 문구를 규칙으로 박으면 다른 도면에서는 틀린 가정이 된다. 항목 목록과 형식만 고정하고 내용은 LLM 이 도면을 보고 채워야 한다
- **회신 이메일**: 고정 템플릿으로 바꾸면 run-2 의 "검사 항목" 절(고객이 명시 요청)이나 run-3 의 정보 요청 구조 같은 적응이 사라진다. 필수 섹션과 필수 수치만 코드로 검사하고 문장은 LLM 단계로 남긴다
- **루트 판정 사유 문장**: 규칙 조항 번호만 찍어 주면 §6 이 요구하는 기술 근거와 상업적 트레이드오프가 빠진다. status 는 코드로, 설명은 LLM 으로 나눈다

## 7. 관찰의 한계

- **같은 도면**: 세 입력의 도면이 모두 같은 파일(ND-IS-042 Rev.A)이다. Step 3 status 와 Step 5 판정이 세 번 같았던 것은 규칙이 안정적이라는 증거가 아니라 입력이 같았다는 뜻이다. ECD 상한 > 0.80(진공 탈락), 질화 valid(ECD ≤ 0.40), valid 루트 0개(CLAUDE.md 의 "대응 불가"), 요청 납기 10일 미만, PDF 파싱 실패 경로는 한 번도 지나가지 않았다. `inputs/README.md` 에 적힌 대로 Helios 메일은 원래 ECD 0.8–1.2 였지만 관찰 전에 도면에 맞게 고쳐졌다
- **독립 표본이 아님**: run-2 는 run-1 기록과 산출물을, run-3 은 run-1·run-2 기록과 Helios 산출물을 읽고 시작했다. 2·3번의 일관성 일부는 선례를 따라 한 결과다(질화 `null`, 가정 문구, 복사 대체 경로). 웹 앱에는 이 선례가 없으니 규칙으로 옮겨 적지 않으면 사라진다
- **채점표 노출**: run-1·run-3 은 `scoring_rubric.md` 를 읽었고, run-1 의 질화 참고값 산출은 채점표를 근거로 했다
- **반올림**: `calculate_quote.py` 의 Python `round(6.55, 1)` 은 6.5 를 낸다(부동소수 6.5499…). 채점표는 6.6 hr / 8.70 을 기대한다. TS 로 옮기면서 `Math.round(x*10)/10` 을 쓰면 6.6 이 되고, 가스침탄 단가가 NovaDrive 8.65 → 8.76, Helios 7.34 → 7.42, Orion 7.84 → 7.92 로 바뀐다(node 로 확인). 결정론 단계라도 반올림 방식을 명시하지 않으면 4단계 재검증에서 로컬 결과와 어긋난다
- **훅 기록**: 성공한 호출만, 필드당 2000자까지만 남는다. run-1 의 24분 공백은 설명되지 않는다

## 판정 근거 요약

- 제어권 축: 실제 순서는 세 번 같았다. 4번째 칸 세 항목은 규칙·템플릿·사람 확인 단계로 흡수할 수 있다. 순서를 모델이 매번 새로 짠 흔적은 없다
- 도구 축: 로컬 에이전트는 파일과 쉘을 썼지만 모두 도메인 함수로 바꿀 수 있다. PDF 읽기는 Claude API 문서 입력으로, Python 스크립트 4개는 TS 함수로, xlsx 는 JS 라이브러리로, `init_customer.py` 는 업로드 저장으로 바꾼다. 런타임에 코드를 새로 써서 실행해야 하는 단계는 없다. 참고값과 xlsx 보정 때 인라인 Python 을 쓴 것은 규칙 빈틈을 메우려던 것이고, 규칙이 생기면 필요 없다
- 따라서 `decision-axes.md` 의 첫 행(코드가 순서를 정함, 도메인 도구, Messages API)에 들어올 수 있다. 다만 아래 조건을 채운 뒤이고, LLM 단계 네 곳(스펙 추출, 누락 스펙, 판정 사유, 이메일)은 순서만 고정하고 판단은 LLM 에 남겨야 한다

판정: 조건부 고정 가능(조건: ① 견적 전제(수량·납기·재질) 누락을 출처 필드로 판별하는 분기 규칙과 사람 확인 단계를 두고 validate_specs 가 null 과 출처를 받게 한다 ② 견적서 생성 함수가 포장·납기·고객 지정 조건·가정 표시·참고 단가를 JSON 에서 읽게 해 사후 보정 단계를 없앤다 ③ extracted_specs·route_evaluation 스키마와 참고 산출 목록(not_suitable 루트 포함, 월 물량, 잠정 시 수량별 표)을 고정한다 ④ 루트 규칙의 모호 조건은 Step 1 추출 필드로 받고, 리드타임 경계·not_suitable 루트 처리·반올림 방식은 수치 규칙으로 적는다 ⑤ 이번 관찰에서 지나가지 않은 루트·리드타임 분기(ECD 상한 0.80 초과, 질화 valid, valid 0개, 10일 미만 납기)를 규칙 함수 테스트로 확인한다)
