# 2단계 판정 (dashboard)

언제 읽나: phase-1 통과, phase-2 미통과.

## 1. 서브에이전트로 판정한다

판정은 **새 컨텍스트의 서브에이전트**가 한다. 관찰을 한 세션이 자기 관찰을 자기가 평가하면 빈틈을 판단으로
메운다. 서브에이전트에게는 `run-1.schema.md` 만 읽히고 아래 프롬프트를 그대로 준다.

## 2. 무엇을 판정하나

「이 출력으로 대시보드가 읽을 데이터 계약을 만들 수 있는가」다. 에이전트의 순서가 아니라 **출력의 모양**을 본다.

- 유일 키 후보가 있는가 — 없으면 실행마다 중복 적재된다
- 갱신 시각 열이 있는가 — 없으면 화면이 언제 것인지 말할 수 없다
- 행 수가 얼마인가 — 많으면 기간 필터가 필요하다
- 민감 열을 어떻게 할 것인가 — 계약의 제외 열로 뺀다
- LLM 문장 열이 있는가 — 길이가 들쭉날쭉해 표에 그대로 싣기 어렵다

### 프롬프트 2 — 고정 가능 여부 판정

```
docs/agent-to-webapp-lite/runs/run-1.schema.md 만 읽고 docs/agent-to-webapp-lite/verdict.md 를 써줘.
다른 파일은 읽지 말 것. 아래 두 절과 마지막 판정 줄로만 구성한다.

## 근거
표 또는 짧은 목록. 유일 키 후보, 갱신 시각 열, 행 수, LLM 문장 열을 각각 한 줄로 적고 그것이 대시보드에
무엇을 뜻하는지 붙인다. 길게 쓰지 말 것.

## 민감 열
민감 열 후보를 어떻게 할지. 대시보드에서 뺄 열 이름을 적는다. 후보가 없으면 '- 없음'.

마지막 줄은 아래 셋 중 하나로 시작한다.
판정: 고정 가능
판정: 조건부 고정 가능
판정: 고정 불가

관찰이 1회뿐이므로 '판정: 고정 가능' 은 쓸 수 없다. 실행 간 차이를 아직 못 봤다.
계약을 만들 수 있다고 보면 '판정: 조건부 고정 가능(관찰 1회)' 라고 쓴다. 4단계 재검증이 확정한다.
유일 키 후보가 '없음' 이거나 열 구성이 실행마다 달라질 것이 뻔하면 '판정: 고정 불가'.
```

## 3. 게이트

```
node $SKILL_DIR/scripts/check_lite.mjs 2
```

두 절과 마지막 판정 줄을 본다. `판정: 고정 가능` 은 거부한다(관찰 1회).

검사가 통과하면 학습자에게 `verdict.md` 를 보여주고 동의를 받는다. 동의하면:

```
node $SKILL_DIR/scripts/check_lite.mjs 2 --approve
```

`--approve` 없이는 통과가 기록되지 않는다. `--batch` 면 묻지 않고 넘긴다.
사람이 판정을 뒤집을 때만 `--override "<사유>"` 를 쓰고, 기록은 `조건부 고정 가능` 이 된다.
게이트는 통과한 판정(override 반영)을 STATUS 의 `verdict` 에 남기고, 뒤 단계는 verdict.md 가 아니라 그것을 따른다.
`--override` 는 2단계에서만 받는다.

## 4. 고정 불가면

게이트가 STATUS 에 종료를 기록하고 라우팅을 출력한다. 그대로 전하고 멈춘다. 3단계 파일을 만들지 않는다.

출력 스키마를 고정할 수 없으면 대시보드가 읽을 계약이 없다. 길은 둘이다 — 에이전트가 출력 형식을 고정하도록
먼저 고친 뒤 다시 오거나, 웹은 파일 내려받기만 두고 표는 만들지 않는다.
